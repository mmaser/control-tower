# Conditional setup and communication

Use this reference when the project is unfamiliar or a missing operating boundary affects the task. An established project with sufficient instructions needs no onboarding ceremony.

## Establish the role when setup is requested

Use the [setup guide](../SETUP.md) for reader-facing instructions and adaptable prompts. Carry out authorized setup rather than handing the user a list of chores the host can perform. First identify the app surface and execution environment, then inspect the effective instruction sources, local/account skill copies, existing coordinator, operational records, and active-session visibility. Distinguish installing a skill from assigning project authority.

1. **Choose the requested scope.** For an unspecified isolated trial, use project scope. Before overwriting any installation, preserve its exact version and local changes. A request limited to project setup does not authorize user/global instruction edits. Verify current host documentation and do not claim a tested install based only on a documented path.
2. **Establish ownership and authority.** Use the chat the user designated or retain the existing coordinator. If choosing would displace another coordinator or is ambiguous, resolve that specific question. Do not create chats without a request. Record the coordinator's stable identity/contact, supported messaging route, and human authorization source. Preserve current publication boundaries and in-flight release ownership; authority cannot be inferred from another agent's request alone.
3. **Integrate durable instructions.** Adapt existing project records and merge a short coordination entry into the effective session instructions without discarding unrelated rules. Check nested/override precedence and specify where current records can be found. Do not publish a documentation change through an auto-deploy trigger solely to complete setup. Workers follow the project agreement without each adopting the full coordinator role.
4. **Bring active sessions on board.** Within existing authorization, send the agreement, current-record source, role, and a request for scope/in-flight-action acknowledgment to relevant project chats. Otherwise prepare user-relayed handoffs. Respect safe boundaries and preserve independent work. Inspect how each active checkout reaches the current records; neither a file edit nor delivery establishes adoption. Record unreachable/unconfirmed sessions and hold only unresolved conflicting actions.
5. **Verify and report.** Confirm skill path/version where the coordinator loads it, effective instruction sources, fresh-worker recognition of the role, and acknowledgments from relevant existing workers. Exercise a harmless readiness handoff when possible. Report these observations separately, with any visibility gaps and next owner. Do not run a release as a setup test. Reuse the verified agreement on future work; repeat only checks affected by a change.

For new projects, establish the minimal agreement before parallel work begins and leave unknown release configuration unresolved until needed. For existing projects, reconcile owners, uncommitted work, release slots, and ongoing operations before changing coordination. For global use, keep only the reusable convention in global instructions; project identities and authority remain in each project. Do not assume local configuration synchronizes to other hosts or active chats.

## Keep ordinary use lightweight

Inspect the current request, applicable instructions, and existing release records first. Discover repository targets, components, release triggers, owners, and tools through available read-only evidence. Do not require the user to answer questions the project already answers, classify their skill level, or populate an entire template before useful work begins.

Ask only about missing intent, authority, or configuration that changes the next action. Bundle related questions when helpful. Mark unresolved facts as unknown and continue independent work. Missing production details may block publication without blocking an inventory or candidate preparation.

When operating boundaries are new or unclear, briefly summarize the agreement supported by the user's instructions: what can proceed, what needs a decision, and what triggers publication. A summary records authority; it does not grant it. Reuse established permission without asking for approval again. Do not turn a setup summary into a mandatory sign-off for already-authorized work.

Use existing documentation. Create or extend a small project record only when durable coordination needs it and the task permits it. Skip fields unrelated to the project. Keep private machine configuration separate from shared copies. Project preferences stay in the project, not in this reusable skill.

Match the user's vocabulary and desired detail. Explain an unfamiliar concept at the point it affects a decision, for example: “This push would also update the public site.” Experienced users can receive the same facts with revision and environment identifiers. Do not invent permanent beginner/expert modes or repeatedly offer tutorials.

Report only relevant facts about work, approval, distribution, and verification. For example, “Saved locally; remote recovery not yet verified; preview ready; publication pending your decision.” These are independent facts: a backup is not approval, and a successful build is not evidence of availability. Include a next action or specific question when needed, with technical evidence linked or recorded rather than pasted into every response.
